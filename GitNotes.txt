* Дефиниция за version control

	Version control-a ни позволява да проследим промените, които сме правили на файл/ове и да възстановим този промени до някакаква произволна версия

* Локални version control systems

	Локални version control systemи пазят историята на всички промени по дадени файлове, като позволяват връщане на произволна версия добавайки съответните промени

* Централизирани version control systems

	Главен сървър съдържа цялата информация относно файловете и много клиенти използват сървъра за да теглят промените.
	Ако примерно се случи проблем със сървъра, може да се изгуби цялата информация, освен ако някой не си пази даден snapshot

* Разпределени Version Control systems

	DVCS позволява цялстно копиране на хранилището както и на неговата история с пачове, тоест всяко копие дава на потребителя цялата история и всички файлове.
	Git работи по този начин

* Как работи Git

	CVS пази промените като колекция от файлове, тоест да си качим една промяна трябва масово да си качиш файловете.
	Защото един вид CVS пита: "Какво си променил в този файл?"

	Докато Git прави верижка от snapshot-ове, всеки shapshot пази единствено как изглежда файла, който си го променил и го запазва така,
	ако примерно не си променил даден файл тогава Git реферира към по-стар снапшот (тоест не го копираш наново)
	Защото един вид Git пита: "Как изглежда целия проект сега?"

	Ето това ти позволява докато използваш Git лесно да променяш между промените ти

* Операциите на Git са локални

	Понеже гит тегли цялостното repo, той тегли и историята на промените (различните снапшоти) и спокойно офлайн може да сравниш дадени промени между файловете

* Чексумите на Git

	Всичко в Git се проследява чрез checksum-и, тоест Git вижда всичко и няма как да изпусне нещо.
	Механизма който Git използва за checksum-ите се нарича SHA-1 и е низ от 40 стринга съдържащ 0-9 и a-f, генерира се базирано на съдържанието на файловете

* Трите възможни състояния за Git

	Когато работим в една директория, в която има repo, Git пази промените в 3 различни състояния:
	- modified (когато сме променили файл и не сме го дали за промяна)
	- staged (подаваме промяната която сме направили и тя би се качила в следващия commit)
	- commited (данните са записани в локалната база данни)

	Тоест имаме и 3 области на работа:
	- working directory // държи всички файлове върху който можем да работим
	- staged directory  // промените който подлежат да бъдат комитнати
	- repository  // git repository-то ни локалната база данни

* Команди който използваме когато конфигурираме git

	git config --global user.name "User Name"
	git config --global user.emal "useremail@email.com"

	--global го слагаме когато искаме подадената информация да важи за всички наши проекти

	git config --global core.editor "'C:/Program Files/Notepad++/notepad++.exe' -multiInst -notabbar -nosession -noPlugin"
	Копи пейст това в терминала, кара git да ни отвори notepad++, когато искаме да пишем commit messageи

	git config --list показва всичките данни който са били конфигурирани

	git config --global init.defaultBranch main // така променяме името на главния бранч, когато създаваме ново репо

* Създаване на Git repo

	Има два начина с който може да се сдобиш с git repo:
	- вече имаш съществуващ проект в директория и в неговата директория го създаваш това git repo
	- теглиш вече създадено git repo от сървъра в избрана директория

	Когато искаш да инициализираш repo, отиваш в дадена директория и пускаш командата: git init 
	Тя ти създава необходимите файлове и вече имаш готово репо

	Когато искаш да клонираш (тоест да изтеглиш repo от сървъра) използваш: git clone <url>
	Тази команда ще ти направи цялостно копие на сървърната страна със история на всички промени.
	Ако репото което клонираш се казва myRepo в папката в която си извикал git clone ще ти създаде myRepo директория.
	
	Ако искаш тази директория да се казва по друг начин използвай това:	git clone <url> myNewFolder

* Запис на промените в хранилището

	Всеки един файл в твоето хранилище може да бъде: tracked или untracked
	Tracked са тези файлове, който git познава, тоест от последния snapshot или вече stage-натите. Могат да бъдат modified, unmodified, stagged
	Untracked файловете са тези който не са в staging area-та или не са от последния snapshot

	Примерно ако изтеглиш ново repo всички файлове ще бъдат tracked (защото  са от последния snapshot) и unmodified (защото не си ги променял)
	Примерно файловете който са ново създадени или никога не са били в Git са untracked 

* Проверка на статуса на файловете

	Основната команда е git status, тя ти показва кой файлове са в staging area-та, кой са untracked, на кой бранч се намираш също

* Добавяне на нови файлове в staging area-та

	Това става чрез командата: git add <името на файла>

	Това ще накара променен файл да бъде добавен в stading area-та.
	Ако примерно си забравил да добавиш нещо преди да комитнеш и правиш нови промени в файл-а който преди малко си преместил в staging area-та.
	Ще трябва отново да добавиш новите промени в staging area-a или иначе няма да се добавят в следващия commit.

* Игнориране на файлове

	За да може Git да игнорира файлове, може да създадем файл с името .gitignore и в него да са написани кой extensions трябва да се игнорират:
	- За пример: *.тxt ще игнорира .txt файлове

* Публикуване на промените

	Става дума относно commit-ване, не забравяй само всичко което е в staging area-та ще бъде commit-вано, използвай командата: git commit

	Ако си написал git commit, ще ти се отвори текстовия редактор който си въвел с git config core.editor, за да напишеш комит съобщението

	Може да използваш git commit -m "Message" за да стане по-бързо

	Когато комитнеш ще ти излязат:
	- колко файла си комитнал
	- към кой бранч си комитнал
	- каква е чексумата

	Можеш и да използваш git commit -a -m "Commit Message" директно да комитнеш modified файловете

* Изваждане на файла

	Ако имаш файл file.txt, командата git rm file.txt ще:
	- изтрие самият файл
	- ще stage-не тази промяна

	Ако искаш да изтриеш file.txt в който има нови tracked промени, тогава използвай: git rm -f file.txt
	Или иначе ако използваш само git rm, няма да ти е позволено

	Ако искаш да махнеш файла от staging area-та, но да остане на диска използвай: git rm --chached file.txt

* Преименуване на файл

	Ако искаме да преименуваме вече съществуващ файл: git mv <oldName> <newName>

	Следната команда прави:
	- преименува самият файл в newName
	- премахва старият файл с git rm
	- добавя новия файл с git add

	Пише че се добавя чрез git add и git rm, но Git вижда това като преименуване

* Преглед на историята

	Можем да прегледаме историята на комитите чрез git log, като най-новите промени са най-отгоре, показва ти и:
	- чексумата
	- името на човека комитнал
	- имейла му
	- датата на комита
	- и съобщението при комит

	Ако използваш git log -p или git log --patch ще ти излезе както по горе описаната информация, така и самите промени в кода който са направени при всеки комит
	Обаче ако искаш да видиш по съкратена версия на промените в кода може да използваш git log --stat

	Ако примерно не ти харесва самият структуриран текст може да използваш git log --pretty
	Има и възможност да ти покаже граф и на снапшотите git log --graph

	Запомни че авторът е различен от комитаджията, aвторът е този който е променил файла, а комитаджията е този който е комитнал

	Може да провериш последните 2 седмици какви комита са слагали чрез: git log --since=2.weeks
	Може да търсиш и чрез ключова дума -S между комиттите: git log -S function_name
	Може да зададеш и в какъв формат искаш да ти излязат нещата: git log --format="%h - %an, %ar : %s"

* Възстановяване на направени действия

	git commit --amend ти позволява да промениш последния ти комит вместо да създаваш нов, обаче тази команда и ще ти отвори текстовия редактор, за да напишеш ново съобщение
	git commit --amend --no-edit ще ти запази старото съобщение

	Прави следните неща:
	- Дава ти възможност да промениш комит съобщението
	- Дава ти възможнсот да промениш/добавиш файлове към последния snapshot

	Важно!!! git commit --amend ти пренаписва историята, тоест добра практика е да не го използваш за комити който вече са push-нати в споделеното repo 

	Пример как да го използваш правилно:
	git commit -m "Initial commit"
	git add forgotten_file
	git commit --amend

* Изваждане на файла от commit stage-a

	Може да използваме git reset HEAD <fileName>

	Ако примерно си сложил два файла в staging are-a може да използваш горната команда, за да преместеш единия в working directory-то

* Отмяна на промените в променен файл

	Ако си направил промени във файл, който още е в working directory-то и да му махнеш промените: git checkout -- <fileName>

	Това ще discard-не промените и ще ги изтрие, като върне <file> до съдържанието което е имало в последния комит

* Възстановяване с git restore

	git restore прави същите неща който git reset Head прави и git checkout -- също

	Ако искаме да махнем даден файл, който сме променили от commit stage-a: git restore --staged <fileName>
	Ако искаме да махнем промените на даден файл, и да го върнем до състоянието му в последния комит: git restore <fileName>

* Работа с отдалечени repo-та

	Remote repo-тата се намират в мрежата или сървъра откъдето теглиш проекта (примерно GitHub или GitLab)

	Може и да се използват и remote repo-та на текущият компютър на който работите, факта че пише remote означава че се запазва някъде в Git.
	
	Използвай git remote, за да видиш отдалечените хранилища, който имаш конфигурирани на компютъра.
	Ако си клонирал някое remote repo трябва да видиш поне origin - това е името което Git дава от сървъра от където си клонирал

	Чрез git remove -v може да видиш и самите remote repos къде сочат като url

* Добавяне на remote repo

		Понеже когато клонираш отдалечено репо, git дава името origin от Url на репото от което си дръпнал

		Ако искаш да добавиш ново repo от което да изтеглиш правиш с командата: git remote <shortname> <url>
		Shortname служи за псевдоним за url, просто може да използваш името вместо Url-a

		Ако после искаш да изтеглиш от самото repo новата информация правиш: git fetch <shortname>

* Fetching и Pulling на данни от repo-та

	Командата която изтегля всички данни, който нямаме локално от remote repo: git fetch <remote>
	Командата също ще ти изтегли и бранчовете което има в това repo и ще можеш да си слееш промените локално

	Когато git clonesh дадено репо, git автоматично ще създаде remote repo с името origin, тоест ако искаш да си актуализираш промените използвай git fetch origin
	Не забравяй, че git fetch origin не ти слива автоматично промените, ти сам трябва да го направиш това

	Обаче командата git pull автоматично ти тегли промените и автоматично ти ги слива с master branch-a

* Изпращане на данни към отдалечено хранилище

	Ако си имал промени в локалното си repo и искаш да го качиш в remote repo,то използвай: remote push <remote> <branch>
	Пример remote push origin master (origin е url-a на repoto онлайн от което си теглил, а branch ти е brancha който искаш да вкараш)

	Ако примерно някой друг колега е сложил промени преди теб относно същата програма в която си работил, трябва първо неговите промени да изтеглиш, да ги слееш и след това да ги изтеглиш

* Преглед на отдалечено хранилище

	За да провериш повече информация относно remote repo-тата използвай: git remote show <remote>

	Ще ти предостави информация относно:
	- Откъде fetch-ваш (url) и къде push-ваш (url)
	- Информация относно ти какви бранчове имаш
	- Информация относно remote branches (тоест другите branchove в remote repo-то)
	- Показва ти ако git pull-неш даден local branch от кой ще изтегли новата информация (ще бъде remote branch ) и ще слее промените
	- Показва ти от кой local branch можеш да вкараш промени за да влязат в remote branch

* Премахване и преименуване на отдалечените хранилища

	За да преименуваш името на remote repo: git remote rename <oldName> <newName>
	Това също ще промени и пълните имена на бранчовете който са свързани към remote repo-то, тоест ще станат от <oldName>/<branchName> на <newName>/<branchName>

	За да премахнеш remote repo: git remote remove <repoName>
	Единствено се премахва url връзката, което имаш към това remote repo, но си остават данните на твоя компютър 

* Тагове за версия в git

	Можем да създаваме различни версии в различен етап на разработката ни в Git

	Можеш да видиш текъщите версии с: git tag
	Можеш даже да видиш и тага по определен стринг: git tag -l "1.2.4*"

	Има два основни типа тагове: lightweight и annotated.

	Lightweight сочи към даден комит
	Annotated отновно сочи като lightweight към даден комит, но този път има повече информация към тага като имейл, име на човека който е направил tag-a и описателно съобщение

	За да направим annotated tag използваме: git tag -a <version> -m "Message initial", ще ти излезе текстов редактор за да си напишеш комит съобщението
	После може да използваш git show <tagVersion>, за да ти покаже по-подробна информация за тага

	За да създадеш lightweight комит: git tag <versionVersion> единствената информация която пази този таг е чексумата на камита който е записан във файла
	Ако искаш да видиш lightweight тага с git show ще ти излезе само комита към който сочи

	Ако си изпуснал да направиш даден комит на таг можеш спокойно да се върнеш като използваш чексумата на комита който искаш да е версията:
	git tag -a <versionName> <checksum>

	Когато създадеш един таг, той не се push сам, а ти трябва да го направиш ръчно:
	git push origin <tagName>
	Ако имаш много тагове и искаш наведнъж да ги направиш даваш: git push origin --tags

	Ако искаш да изтриеш таг от локалното си хранилище ще трябва да използваш: git tag -d <tagName>, обаче това няма да го изтрие от remote repo-то
	За да изтриеш даден таг от remote repo трябва да използваш git push origin --delete <tagName>, един вид буташ промяната, че този таг го триеш

	Можеш да се върнеш към стар таг чрез git checkout <tag>, но трябва да си внимателен, но трябва да си внимателен защото ще влезеш в DETACHED HEAD състояние
	Тоест вместо да сочиш към master brancha, ти сочиш към нищо и ако комитнеш нещо сега ще са ти загубени промените.
	Най-safe е да създадеш нов бранч от този таг и да го merge-неш с master: git checkout -b <branchname> <tagname>

* Псевдоними

	Позволява ти да можеш да съкратиш командите който пишеш често и да имаш свой псевдоним за няколко команди наведнъж
	git config --global alias.st status, сега вместо git status може да напишеш git st
	git config --global alias.unstage 'reset HEAD --', ако напишеш git unstage ще ти изпълни git reset HEAD -- командата

* Branching като цяло

	Branching означава, че се отделяме от главния branch и промените който правим, не се прилагат върху главния бранч на момента

	В повчето vc системи си принуден да копираш цялата директория на файловете който искаш да промениш и това отнема много ресурси

	Не забравяй, че Git не пази точно разликите който си направил между комитите, а когато комитнеш Git прави снимка на сегашното положение на файла,
	а и после между комитите се сравнява състоянията на файловете и така ти показва разликите

	Тоест когато комитнеш Git прави един commit обект, който съдържа:
	- snapshot-a на файловете който са били в staging area-та
	- името на автора
	- комит съобщението
	- указател, който сочи към предишният комит

	Първоначалния комит няма родители, един нормален комит има само един родител, ако имаш комит който е резултат от merge тогава имаш няколко родители

	Първоначалния комит на едно репо винаги се казва master/main, който винаги сочи към най-последния ти комит (Това, че се казва master не го прави по-специален)

* Създаване на нов branch

	Правене на бранч става с тази команда: git branch testing
	Новият бранч testing ще сочи към комита който си направил в момента (тоест на сегашното състояние)

	HEAD е главния указател и той сочи към най-последния комит който си правил, в момента на създаването на brach testing,
	HEAD сочи към master, това е така, защото не си превключил на testing

	Чрез git log --decorate може да видиш и HEAD към кой бранч сочи

* Превключване към бранч

	За да се превключиш на друг клон използваш git checkout <branchName> (С други думи местиш самият HEAD указател)

	Ако искаш да превключиш на бранча testing и комитнеш нещо към него HEAD ще сочи на един комит напред, защото master бранча още не е пипан.
	Ако ти решиш да git checkout master без да запазиш файловете от предишния комит в testing, той ще се премахнат и HEAD отново ще сочи към master.

	Когато искаш да видиш истроията на комитите използвай git log -all или git log <branchname>

	Може и да използваш: graph log --oneline --decorate --graph --all

	Ако искаш да направиш бранч и веднага да се прехвърлиш на него git checkout -b <branchName>

* Реален пример, който може да ти се случи докато работиш

	1. Създал си си бранч от master branch-a и разработваш нов feature
	2. Сложил си няколко комита в този твоя бранч

	Възможно е по някое време да ти кажат че трябва да работиш по друг проблем

	1. връщаш се обратно на master brancha
	2. създаваш си нов brach Който да оправиш нововъзникналия проблем
	3. чакаш да се слее hotfix-a в продуктовия код (master)
	4. продължаваш да си работиш на бранча за новия feature

* Merge–ване на бранчове

	Ако имаш master бранча и почнеш да работиш по някакъв feature на нов бранч: git checkout -b feature
	След като приключиш работата с бранча отиваш на master бранча и пишеш git merge feature
	Това е fastforward!!! Защото ако в master няма никакви промени след създаването ти на бранча, просто самият HEAD се мести напред

	Изтрии бранча с git branch -d feature

	Ако имаш бранч по който си работил по някакви неща, обаче в master бранча вече имаш нови промени, ще трябва да слееш
	Тук git ще направи merge commit!!! merge commit-a има два родителя, 1ният е последния комит в клона който сливаме (master), 2рия е последния комит на бранча ни

* Конфликти при бранчовете

	Да кажем, двама човека работят по един файл на едно място на два различни бранча, после при merge-ване това би предизвикало merge conflict

	При още командата merge conflict ще изпише, че автоматичното merge-ване не е минало.
	Командата git status в случай, може да ти покаже кой файлове са unmerge-нати

	След като git status ти покаже къде имаш conflict в самият файл, ако отидеш git Ще ти е заобрадил с <<<<< >>>> зоната на конфликта
	Там ще трябва да избереш едната имплементация между ======= като отгоре пише кой код на кой бранч принадлежи

	След като си избрал кое да фикснеш, правиш git add <fileName> за да добавиш промяната в stading area-та
	След това може директно да комитнеш с git commit -m ... и последния комит ще се брои към верижката на merge requesta

* Управление на клонове

	с git branch може да видиш другите бранчове, като със звездичка показва този на който си (HEAD сочи към него)

	с git branch -v може да видиш и последните комити към бранчовете

	с git branch --merged може да видиш клоновете който са се слели, тези клонове които се появят и нямат звездичка могат да се изтрият с git branch -d

	с git branch --no-merged ще ти излязат тези клонове който не са merge-нати, ако искаш да изтриеш клон който още не е merge–нат използвай git branch -D

	Може да дадеш и името на бранч за да видиш кой бранчове са се mergenali към него с git branch --merged master

* Преименуване на branch

	Преименуване на бранч става с git branch --move <oldName> <newName>

	Тази промяна се случва само локално, трябва да я добавиш и в сървъра: git push --set-upstream origin <newName>
	Сега си добавил новия бранч там, но не си махнал стария от сървъра: git push origin --delete <oldName>

* Смяна на името на master клона

	!!!Важно: Смяна на именато на бранч на master/main ще счупи интеграциите и build/release скирптовете, които твоето хранилище ползва

	След като промениш даден бранч на main: git branch --move master main
	Полсле трябва да вкараш промяната в сървъра: git push --set-upstream origin main

	Ще видиш че в отдалеченото репо ще имаш както main бранч така и master branch, обаче колегите ти ще използват още master бранча

	Преди да изтриеш master branch-a, трябва да направиш:
	- корекция на build, release Скриптовете да сочат към правилният бранч
	- корекция в Spec-a вместо master да показва Main
	- затваряне или сливане на всички mergerequesti в стария клон
	- всички проекти които са зависили от master ще трябва да си обновят конфигурациите

* Дълго използвани клонове

	Когато работиш на голям проект, може да срещнеш следния начин за разработка:
	- имаш един главен бранч, който се нарича master (най-стабилния код)
	- имаш отделен бранч от master, който е develop, но не е още много стабилен, но стане ли се слива в master
	- develop се използва за създаването на (topic branches), в който се имплементират функционалности и като се видят че работят се сливат в Develop

* Topic branch

	Topic branch се създава, когато искаме да имплементираме някаква функционалност, след нейното имплементираме тя се вкарва в develop.

	Това е един плюс на Git, че ти ако имаш няколко topic brancha (за различни функционалнисти, който имплементираш) можеш лесно да се прехвърляш
	от един брач на друг и ти позволява лесно да се запазиш промените и ако дори се наложи след някакво време ти пак можеш да merge-неш нещата си.

* Отдалечени клонове (remote branches)

	Когато някой си е качил бранча в remote repo-то, това ще се казва remote branch

	Когато ние git fetch-нем от нашето remote repo ние ще имаме в нашата локална машина remote-tracking branchove, който имат указатели към самите remote repo-та.
	Те автоматично се местят напред, когато ние се свържем със сървъра и се види че има някой друг нов комит в този remote branch

	Та ако имаш конвенцията за следване на име на remote brancho-ове е <remote>/<branch>
	Ако искаш да видиш някой бранч в remote repo origin правилното име ще е remote/repo

	Може да използваш командите git remote show <remote> за да видиш другите remote branchove към даденото remote repo

* Изпращане към сървър (pushing)

	Ако имаш локален branch в който имаш промени и искаш да го споделиш с другите, трябва да го качиш в remote repo.
	Твоите локални клонове не се качат директно в remote repo-то а трябва сам да ги качиш, това нали ти позволява както да имаш
	локални бранчове така и отдалечени бранчове

	С git push <remote> <branch> качаш локалния ти бранч към git сървъра

	Когато качаш клона Git автоматично му разширява името на refs/head/serverfix:refs/heads/serverfix, което означава "вземи локалнип ми
	бранч serverfix изпрати го в remote repo-то, обновявайки remote branch-a serverfix"

	Moже даже да използваш командата git push origin serverfix:serverfix, превода е буквално "Вземи ми локания бранч serverfix и го слей с отдалечения бранч serverfix"
	
	Когато git fetch-неш за да изтеглиш новосъздадения remote branch ти не получаваш автоматично техните копия.
	Няма да имаш действителното съдържание на клона а само указателят който сочи към origin/serverfix, който не можеш да променяш 
	
	За да видиш промените, трябва да го слееш с текущия си бранч с git merge origin/serverfix, а ако искаш това да стане на друг бранч
	използвай командата git checkout -b serverfix origin/serverfix (дава ти клон в който да работиш от последния snapshot в който е origin/serverfix)
	
* Проследяване на клонове 

	Tracking branch е този бранч който е създаден локално, за да извлече данни от remote-tracking branch-a и клонът който този tracking branch следи се нарича upstream branch 
	Tracking branch-овете са локални бранчове, които имат директна връзка с отдалечените бранчове, тоест ако използваш git pull в този tracking branch, Git ще знае от кой бранч да изтегли промените и къде да ги слее
	
	Нали когато клонираш дадено remote repo се създава master бранч, който е tracking branch на origin/master, може и друг remote branch да проследиш:
	- git checkout -b <branch> <remote branch> ти позволява да създадеш локален бранч който да е tracking branch за <remote branch>
	- git checkout --track <remote branch> е съкратената версия на командата от горния ред 
	- git checkout <remote branch> е още по кратка версия
	
	Ако имаш локален бранч и искаш да го накара да следи даден remote branch: git branch -u <remote/branch> (ама трябва да си на този бранч)
	
* Upstream съкращения 

	Когато имаш настроен tracking branch, който си сочи към неговия upstream branch, можеш да се обръщаш към upstream brancha със @{u}
	Тоест ако искаш да merge-неш промените от git merge origin/master трябва да напишеш git merge @{u}
	
	За да видиш какви проследяващи клонове имаш може да напишеш git branch --vv, тук ти показва локалните tracking branch-ове, колко комита са напред/назад и към кое remote repo сочат 
	 
* Pulling (изтегляния и сливания)
	
	Както знаеш командата git fetch, изтегля всички промените които нямаш локално, но не променя самата работна директория.
	За да я промениш трябва да използваш командата git merge.
	
	Командата git pull реално ти върши и двете както ти тегли и самите промени така и ти ги слива автоматично
	
	Ако в този случай имаш някакъв tracking branch, то git pull ще потърси към кое remote repo и кой remote branch се следят от текущия локален клон,
	след това ще изтегли новата информация и ще я слее 
	
* Изтриване на отдалечени клонове 

	Можеш да изтриеш remote branch чрез командата git push origin --delete serverfix 
	
	Това само ще изтрие указателя от сървъра, Git за малко ще пази и самите данни, но след време неговия garbage collection ще мине през неизползванните
	данни и ще ги изтрие 
	
* Пребазиране на клонове (git rebase)

	Съществуват два основни начина за интегриране на промени от един клон на друг: git merge и git rebase 
	
	Най-лесния начин за интегриране на промени на клонове, беше командата merge.
	Да кажем че имаш два бранча master и featura и вече по feature си бутнал няколко комита и искаш да ги слееш в master.
	При merge commit-a ще вземе последния снапшот при featurea бранча и при master бранча и ще вземе последния им предшествени и базирано на тези промени 
	ще си направи съответния merge
	
	Ако използваш командата git rebase master в клона my-feature branch Git ]Ще направи следното:
	- намира най-последния общ предшественик за snapshot 
	- запазва ти промените в git my-feature branch във временна памет
	- backtrack-ва обратно този my-feature бранч до последния предшественик
	- добавя промените, който ги е имало в master, но ги е нямало в git my-feature branch 
	- чак тогава добавя промените който оригинално са били направени в git my-feature branch
	
	Предимстваната на git rebase е да поддържа по-праволинейна история на комиттите 
	
	Това е най-важното което трябва да знаеш, за да внимаваш като използваш git rebase:
	Не пребазирайте къмите, които съществуват извън твоето локално репо и върху които други хора може да са базирали работата си. 
	
* Git сървър 

	Git сървър е буквално remote repo, към което имат достъп всички и теглят и изпращат код през него.
	
	За да пуснем git сървър ще трябва да изберем протоколите, който поддържат комуникацията между репото и хората които го ползват 
	
	Bare repo е един вид голо хранилище, единственото нещо което съдържа е .git директорията му, то служи като склад само за код 
	
* Комуникационни протоколи 

	Git използва 4 основни протокола за трансфер на данни:
	- локален 
	- HTTP
	- SSH (secure shell)
	- Git протокол
	
	Локален протокол:
	Ако Git Servera се намира просто в друга директория, ние ще използваме локален протокол, ние изпращаме данни, клонираме и теглим данни от файлово-базирано repo.
	За да изтеглим такова репо вместо да подадем url, използваме пътя към него пример: git clone fie://<directory> (това file:// Се използва за яснота, Git да знае да не търси в мрежата, а в папката която е посочена)
	
	Ако искаш да си добавиш local repo-то като remote repo в твоя git проект използвай: git remote add local_proj file://<directory>

	Предимства: 1) всичко е доста бързо понеже се случва на диска 2) доста просто е всичко, понеже няма нужда от настройки на сървъра 3) може да се работи офлайн 
	Недостатъци: 1) ако дискът на който работим се повреди, може да се загуби всичко 2) няма web интерфейси 
	
	
	HTTP протоколите:
	SmartHTTP е протокола който е най-популярен днес, използва се от GitHub, GitLab
	Имаш едининен url адрес за всичко, тоест url който отваряш да теглиш кода и да качваш и да гледаш кода вътре е същия 
	Няма някакви сложни SSH ключове за автентикация, използва се просто HTTP автентикация като пишеш име и парола 
	
	Предимства: 1) доста е удобен, понеже има url адрес за всичко 2) лесна авентикация, вместо да използваш ssh ключове, използваш име и парола 3) универсален достъп 
	Недостатъци: 1) може да е по-бавен, защото в комуникацията носи http хедъри 2) трябва да въвеждаш паролата си, вместо автоматично да удостоверявш с SSH ключове 
	
	SSH протокол:
	SSH достъпа предлага сигурна, криптирана връзка. Можеш да копираш git repo с ssh:// и за да се автентикираш използваш потребителско име и SSH ключ
	
* Избор на комити 

	Можеш да избереш да погледнеш единичен комит в гит чрез: git show <checksum>
	Чексумата може да бъде между 6 и до 10 символа и Git ще ти я намери 
	
	Чрез git log --abbrev-commit --pretty=oneline може да видиш и всичките комити направени, като чексумата е съкратен вариянт
	
	Може и да видиш какво представлява последния комит към даден branch: git show <branchName>
	
* Git сташване 

	Командата git stash ти взима промените (който още не са готови за комитване), пакетира ги и ги запазва на сигурно място като 
	оставя работната ти директория чиста все едно туко що си направил комит 
	
	За да си запазиш промените в сташа и да дадеш описание към сташа: git stash push -m <stashMessage>
	За да добавиш и untracked files към stash-a: git stash push -u -m <stashMessage>
	
	За да видиш лист на всички запазени сташове: git stash list (stash@{0} е най-скорошния)
	
	За да искаш да приложиш промените от stash-а ти (и след това да бъдат изтрити от сташ листа): git stash pop
	Знай, че само ти връща промените от най-скорошния сташ (stash@{0})
	Ако пък искаш определен сташ да сложиш (примерно git stash pop stash@{1})
	
	Тази команда прави същото като git stash pop, но не трие промените
	git stash apply // най-скорошния stash 
	git stash apply stash@{1} // някакъв по твой избор
	
	За да видиш кой файлове са променени, като сбита информация: git stash show stash@{0}
	За да видиш пълните разлики във файловете на сташа: git stash show -p stash@{0}
	
	Ако искаш само единични промени да прехвърлиш във stasha: git stash push --patch 
	(Тук git ще те пита ред по ред промяна дали искаш да я запазиш във stash-a)
	
	За да изтриеш най-скорошния stash: git stash drop
	За да изтриеш специфичен stash: git stash drop stash@{1}
	За да изтриеш всички сташове: git stash clear
	
* Git cherry-pick

	git cherry-pick ти позволява да отидеш на даден бранч и да избереш комит от него и да го приложиш върху друг бранч
	
	Реален сценари за употреба:
	Представи си, че в main branch-а има даден бъг, но същия бъх се намира и на бранча myBranch, чрез командата 
	git cherry-pick ще можеш да приложиш комита, който е фиксанл проблема в main brancha в myBranch
	
	Намират комита, който реално е фикснал проблем, примерно с git log --oneline
	отиваш на бранча, на който трябва да приложиш този комит примерно git checkout myBranch 
	изпълваш командата git cherry-pick <checkSum> 
	
	Note!!!: Когато приложиш cherry-pick този комит ще бъде най-новия в git log-а 
	
	Можеш да избреш няколко комита: git cherry-pick <checksum> <checksum>
	
	Ако искаш да вземеш информацията от избрания комит, но без да правиш автоматичен комит
	git cherry-pick --no-commit <checksum> (след това промените от комита ще влязат в staging area-та)
	
	Ако искаш да редактираш съобщението, защото не ти е харесал
	git cherry-pick --edit <checksum> (това ще ти отвори текстовия редактор)
	
* Git revert и Git reset 

	При подадена хешсума git вижда какъв е комита и прави нов комит, който е обратното на неговото (с други думи маха промените, който са били интегрирани с този комит)
	git revert <checksum>
	git revert прави нов комит, за да каже окей ние от този комит махнаме тези промени 
	
	git rest служи за манипулирането на историята на комитите, като основната и функция е да премести HEAD указателя към по-стар комит 
	За разлика от git revert, git reset направо си премахва комити 
	
	Използване на git rest --soft <checksum>
	Премества ти HEAD указателя към посочения комит, staging area-та и working directory-то остават непипани,
	всички промени от комитите който са били след <checksum> ти се добавят в staging area-та.
	
	Използване на git reset --mixed <checksum>
	Премества HEAD и изчиства Staging Area-та, обаче working directory-то си остава непипано
	Всички промени от комити след <checksum> няма да се намират в staging area-та, а ще се намират в working directory-то
	(Ако само напишеш git reset <checksum> по default ще си извика --mixed)
	
	Използване на git reset --hard <checksum>
	Премества HEAD и изчиства staging area-та и в working directory-то
	
	git reflog ти показва всички твои действия, които си променил върху HEAD на някой клон.
	Записва всяко твое commit, reset, merge, reverd абе всичко което е преместило HEAD.
	Този дневник е локален за твоя компютър и не се качва в отдалеченото хранилище
